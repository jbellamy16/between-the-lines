## Frozen comparison

`frozen.json` stores the full synthetic inputs, cutoff, preferences, catalogue, complete initial B2 evidence, B2 decision trace, stories, answers, criteria and source hashes. `offline-measurements.json` records actual local B2 timings; provider requests and cost are zero. Model results, tokens, latency and cost are **null/unmeasured**, not simulated successes. The SHA-256 of canonical `JSON.stringify(frozen)` identifies this proposal. The later authorization must bind that digest and the reviewed execution commit.

One development scenario: **fading-favored**, at 30:00, score 0–0, with Harbor preferred. Harbor's shots rise 2→6, but its recent halves fall 5→1. Riverside rises 1→5 and its recent halves rise 2→3. Mean source xG per shot remains 0.1. Harbor has two recovery-to-shot possessions; Riverside's repeated-route interpretation is limited. Both teams' increased activity is supported. This creates a real prioritization tradeoff between larger totals, preferred-team interest, temporal counter-evidence and opponent activity.

Unchanged B2 already leads with **“Riverside: more shots”**, performs two evidence reads (plus independent verification), retains all four guided answers, and foregrounds opponent improvement, chance quality and competing explanations. It stops `sufficient`. The investigator receives the same catalogue and **all** successful B2 reads, including qualifications. PR #40 omits optional initial display rows from the wire packet but preserves calculations, references and delivery disclosures. Nothing is hidden from B2 to manufacture an advantage.

Separate control: **quiet-no-call**, an empty synthetic event prefix at the same cutoff. B2 has no story and stops `no-material-gain`. The investigator runs in `normal` mode with network explicitly prohibited and must return the deterministic result with zero attempts. This tests the application no-call policy; it does not demonstrate model restraint.

Compare three distinct records: frozen B2, actual Foundry-backed verified output, and actual provider-selected read/final decisions. Invalid raw structured decisions are retained (bounded to 16,000 characters per item), separately from the safe fallback. Hidden reasoning is neither requested nor saved. This is an authored development case, not a holdout or a statistically meaningful preference study.

More retrievals, valid IDs or reordered IDs alone do not establish improvement. Count rejected structured decisions separately; fallback safety does not earn model capability credit. Operational feasibility requires an uncached verified selection, relevant interpretation/challenge, safe publication and complete reconciled accounting within every cap. Demonstrating **value beyond B2** additionally requires the cited human review. Expected plausible outcomes are parity, regression, invalid-plan fallback, cap-limited/inconclusive, or blocked. Do not keep trying until a favorable result appears.

## Limits and spending safeguards

- One investigator workflow, one separate deterministic control, **at most two HTTP attempts and $0.50**, with every lower existing application limit and authorization ceiling still binding. Frozen local ceilings are `[2,2,2,2,30,30000]` for minute/hour/day/total workflows and request/token throughput. No limit is increased.
- The PR #40 runner gains only an optional downward attempt cap (0–3, invalid values fail closed), included in cache identity. Two attempts permit one read then a forced final; a retry consumes that same allowance. Existing provider pacing, Redis reservations, cooldowns, payload limits, 1,800 output-token allowance, timeouts, cancellation, verification and success-only caching remain active. The additional study transport stops at the first HTTP failure, so it can be stricter than the provider retry policy.
- Reserve **$0.3081** durably before each dispatch: 400,000 input tokens at $0.75/M plus 1,800 output tokens at $4.50/M. This reserves the whole documented context and exceeds the documented maximum input; it does not rely on the bytes/token heuristic. Confirmed usage settles that study reservation at uncached rates. A second reserve requires the first charge to be ≤$0.1919. Unknown usage retains $0.3081 and stops; two uncertain reservations cannot fit under $0.50.
- Rates checked on October 12: input $0.75/M, cached input $0.075/M, output $4.50/M. See the exact Microsoft retail-price query and returned meters in `read-only-readiness.json`; model bounds come from [Microsoft's model documentation](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/models-sold-directly-by-azure#gpt-54). The runner rechecks deployment and pricing before launch and refuses drift.
- Require an **already existing** Redis URL, non-expiring complete application counters, a matching existing owner identity, AOF enabled with `appendfsync=always`, no eviction, successful AOF writes and no loading. Missing/unknown/corrupt state blocks execution. There is no initializer, counter reset, refund of application reservations, Redis configuration mutation, cloud provisioning or capacity change.
- Historical `{second-look-ai}:study:*` stores are refused outright. They are not spare allowance. A permanent study claim and atomic Redis journal prevent concurrent starts, restart/rerun, overlapping attempts and budget overspend. A crash or lost accounting acknowledgment leaves the claim/reservation in place. Never remove it to rerun.
- Source, scenario and B2 hashes are checked before execution. Output uses an exclusive directory and exclusive files. Secrets, credential URLs and provider error bodies are not logged. A locally supplied existing API key is required; the runner does not retrieve keys.
